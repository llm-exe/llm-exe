## Summary

- No open `testing`-labelled issues, so picked up the highest-value lead carried forward by the last four runs: line coverage is saturated, and the suspected `safeRequestUrl` URL-userinfo redaction gap was the standing behavioral probe.
- **Confirmed it is a genuine bug.** `safeRequestUrl` (`src/utils/modules/redactSecrets.ts`) redacts secret-bearing query params and then runs a generic `redactSecrets` pass, but never inspects `URL.username` / `URL.password` — so `https://admin:hunter2@api.example.com/v1` leaks the password verbatim into error messages and debug logs. Verified empirically against the real implementation before writing any assertions.
- Established the precise boundary: a password matching one of the `TOKEN_MASK_REGEX` shapes is only *incidentally* partial-masked (4-char prefix/suffix preserved) as a side effect of the generic pass; ordinary short or mixed-charset passwords match nothing and leak in full. The query-param path works correctly even with userinfo present, which is what made the gap easy to miss.
- Filed #747 (`bug`, milestone v3.1.0; **not** `breaking` — it changes only redacted log/error string content, not public API shapes or types). Did not touch source, per agent scope.
- Added 7 tests. The four bug-exposing cases use `it.failing(...)`, so they pass while the bug exists and flip to failing the moment userinfo redaction lands — the suite stays green now, and the fix is self-announcing. Three regular tests pin adjacent correct behavior so a fix cannot silently regress the surrounding redaction.
- `npm test` 198 suites / 3008 tests passing (up from 3001); `npm run typecheck` clean.
