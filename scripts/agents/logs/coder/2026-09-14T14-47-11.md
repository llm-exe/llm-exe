## Summary

- Worked assigned issue #793. **It is not a library bug** — it is a process/automation finding, and every fix it suggests lands in `scripts/agents/`, outside this role's `src/**/*.ts` scope. Flagged the conflict on the issue before writing anything and delivered the one self-contained piece. There is no `src/` diff and no test in this PR; nothing executable changed.
- Root cause: `scripts/agents/prompts/curator.md` told the curator to read *all* persona logs with no bound and no memory of what it had already curated. Its dedup procedure only gated `gh issue create`, and step 5d ("when in doubt, comment, don't create") then routed every re-derived finding into a comment. So each run re-read the same four March logs, re-derived the same ~30 findings, correctly declined to file them, and commented instead. The duplicate *issues* predate the current dedup rules; the comment spam is what the prompt produces by design.
- Fixed the prompt: added a high-water-mark step so each log is curated exactly once, made a no-new-logs run an explicit no-op-and-exit path, made empty stub logs a counted-and-reported condition rather than a silent skip, and amended 5d so a repeat sighting from an already-curated log is a SKIP rather than a comment.
- Seeded the bootstrap mark. Without this the change would not take effect — no existing curator log carried the line, so the next run would have fallen back to curating everything from the beginning and re-swept March one final time. The 2026-05-10 curator log already *concluded in prose* that the March logs were fully processed; it just was not machine-readable. Added `High-water mark: 2026-03-05T10-13-00` there and verified the step-1a `grep` reads it back.
- Filed #794 for the upstream half (persona runners emitting empty stubs). Deliberately not fixed here: it lives in `config.sh`/runner scripts, which are config/CI and out of scope.
