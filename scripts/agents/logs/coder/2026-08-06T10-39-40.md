## Revision (2026-10-12)
Live-tested against a local ollama 0.34.2 with `qwen3-vl:2b`. Before this PR, a tool-call history replayed to ollama was ignored (the model invented a weather answer instead of using the tool result), and an image tool result was a 400. With it, the model uses the tool result, and images on a tool message reach the model (it named a solid red, then blue, image correctly). One change on top of the summary below: the tool's name is now sent as `tool_name` instead of being dropped, since ollama's /api/chat docs use that field for tool history. The cross-provider contract's ollama "image tool result" expectation, added on development after this run, is updated to the converted shape.

## Summary
- Fixed #706: `ollamaPromptSanitize` sent tool traffic in llm-exe's internal shape because it early-returned on any message whose `content` was not an array — which is every tool-carrying message (`content: null` for a tool call, a string for a tool result).
- Tool handling now runs before that early return: `function_call` (single or array) → `tool_calls: [{ function: { name, arguments } }]` with `arguments` parsed to an object via `maybeParseJSON` (ollama takes an object, not a JSON string), and `role: "function"` → `role: "tool"` with the internal `id`/`name` dropped. `content: null` on a tool-call message normalizes to `""` since ollama types content as a string.
- Updated the two `ollamaExpectations` rows in the cross-provider contract test that had pinned the broken behavior; they now assert the ollama-native shape.
- Verified: `npm test` 196 suites / 2921 tests pass, `npm run typecheck` clean, `npm run lint` reports no new issues in the touched files (the repo's 130 pre-existing lint errors are unchanged).
- Not verified against a live ollama instance — there is no integration coverage for ollama.
