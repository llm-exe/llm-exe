## Summary

- Worked issue #757, picking up the one remaining in-scope item: multimodal Gemini `functionResponse`. The previous run left it blocked because the function-calling docs only show the agentic `function_result` step form, which is not the shape `googleGeminiPromptMessageCallback` emits for `generateContent`.
- **Unblocked it from the public discovery document** (`https://generativelanguage.googleapis.com/$discovery/rest?version=v1beta`), which is authoritative for `generateContent`: `FunctionResponse.parts: FunctionResponsePart[]`, whose only member is `inlineData: FunctionResponseBlob { mimeType, data }`. That settles both open questions — `response` stays a text-only Struct (and stays required), and `FunctionResponsePart` has **no** `fileData` member.
- Replaced `googleGeminiFunctionResponseResult` with `googleGeminiFunctionResponse(name, content)`, which builds the whole `functionResponse`: text blocks flatten into `response.result` exactly as before, image blocks become `parts[].inlineData` via the existing `parseImageUrl`. `parts` is omitted entirely when there are no images, so every existing text path (string, text-only array, arbitrary JSON Struct, empty array) is byte-identical.
- A non-base64 image on a tool result now throws a narrower typed error (`"Gemini tool results can only carry inline image data"`) rather than the blanket "not supported" — a Files API / `gs://` URI is valid on a user message but has no home in `FunctionResponsePart`.
- Flipped the Google `"image tool result"` row in the registry-driven contract table from `{ throws }` to the emitted body, completing the Gemini half of #757's acceptance sketch.
- Verified: `npm test` 199 suites / 3144 tests pass; `npm run typecheck` clean; `npm run lint` reports no new problems (130 errors are pre-existing repo-wide, none in changed files).
